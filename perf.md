# Performance measurements and tradeoffs

Review and benchmarks, 2026-09-26–27, with an additional optimization pass on 2026-09-30. The older [v0.1 measurement](docs/releases/v0.1-measurements.md) recorded 15,417,344 bytes idle RSS on Linux/arm64; it is not a measurement of the current tree. The measurements below use a Linux/amd64 QEMU host. The default Go temporary directory on this host is `/tmp`, a `tmpfs`; benchmarks using `b.TempDir()` there measure CPU and memory but do not measure real storage latency. Disk-backed reruns set `TMPDIR=/home/kitdev/Code` on ext4 and are labeled explicitly.

The implemented changes preserve the current API, UI refresh behavior, exact run metrics, schedule semantics, log retention, and the guarantee that each accepted log frame is durable when `Writer.Write` returns.

| Priority | Workload affected | Opportunity | Expected resource effect |
| --- | --- | --- | --- |
| 1 (implemented) | Many scheduled jobs, especially low-frequency cron jobs | Avoid unchanged schedule-state writes, repeated schedule parsing, and restarting unchanged loops; jump between time-zone transitions | Less idle CPU, SQLite work, and WAL I/O |
| 2 (partly implemented) | High-volume logs or many simultaneous log readers | Use constant-time live-tail eviction and skip sealed file chunks before the cursor | Less CPU per frame and lower read allocations |
| 3 (implemented) | Large run history with the dashboard or metrics page open | Index end time for the metrics scan and retain one compact duration sample per run | Less query CPU and temporary memory |
| 4 (implemented) | Idle daemon or long-running alert batches | Replace the alert poll ticker with a deadline timer | Fewer idle wakeups |
| 5 (implemented) | Large retained history | Select candidates in bounded pages and batch main-store and archive deletion | Lower sweep memory, commits, and storage writes |

### Go performance pass, 2026-09-30

Applied the [golang-performance skill from skills.sh](https://www.skills.sh/samber/cc-skills-golang/golang-performance) to baseline commit `0e20d3c`. CPU and allocation profiles identified reflective definition comparison and temporary definition copies in scheduler reloads, repeated zstd encoder buffer allocation at chunk rotation, and frame-header allocation during archive reads.

`Scheduler.Reload` now stores indexes into its input definitions rather than large copied map values, and compares settings directly with typed slice/map comparisons. Nil and empty collections remain distinct, optional booleans compare by value, and API-only timestamps retain their previous full comparison. Regression tests check every definition field, so adding a field without updating the comparison fails a test.

Each log writer now resets its existing zstd encoder after sealing a chunk, retaining compression buffers while creating an independent compressed stream. Log readers reuse one header and limiting reader per page; raw downloads reuse their newline separator. Accepted frames still flush and fsync before `Write` returns. Tests decode rotated chunks independently and exercise archive/file pagination, recovery, and payload ownership.

The final comparison used Go 1.27.0, Linux/amd64, QEMU Virtual CPU, eight Go processors, and `/tmp` on tmpfs. Baseline binaries were compiled before edits. Baseline and final benchmarks ran sequentially with six samples and `-benchtime=300ms`, with profiling disabled for both. Values below are medians; allocation bytes are rounded.

### Loaded daemon measurements

A Linux/amd64 QEMU end-to-end benchmark drives the Unix HTTP API with eight clients submitting 128 parallel jobs, each producing 32 lines of 1 KiB. Concurrent clients make 64 run-metrics and 64 run-list requests; every job must succeed and its log must reach the archive. On `tmpfs`, with the final encoder settings, five runs completed at 641–747 jobs/s, with 15.3–20.2 ms p95 trigger-and-wait latency, 1.7–2.7 ms p95 metrics latency, 2.0–2.7 ms p95 run-list latency, and 268–270 MB allocated per benchmark burst. A previous encoder setting allocated about 420–424 MB for the same workload; its throughput and API latency ranges overlapped. The measured WAL file grew about 62 KB per completed run, counting both databases; this is file growth, not physical device writes.

With 30,000 older and 500 recent run rows preloaded on `tmpfs`, three end-to-end runs completed at 560–573 jobs/s. The 30-day metrics request took 2.0–2.6 ms at p95, and trigger-and-wait took 20.9–23.2 ms at p95. On ext4, a single loaded run completed at 24.7 jobs/s with 487 ms p95 trigger-and-wait latency, about 8 ms p95 metrics/list latency, and 257 KB of Linux process `write_bytes` per job. The history-loaded ext4 run completed at 26.9 jobs/s with 371 ms p95 trigger-and-wait latency, 4.4 ms p95 metrics latency, and 281 KB `write_bytes` per job. The per-frame file `Sync` is the likely limit for these chatty jobs; removing it would weaken the accepted-frame durability guarantee. These fixtures use fast local shell jobs and one virtualized disk, so they are not capacity guarantees for a deployed host.

## 1. Scheduler: avoid unnecessary work while waiting and reloading

The scheduler changes are implemented in [`scheduler.go`](internal/scheduler/scheduler.go) and [`store.go`](internal/store/store.go).

### Why the previous loop cost resources

Each enabled scheduled job has its own loop. Suppose a job runs at 02:00 daily. At 02:01, the loop calculates tomorrow's 02:00, writes it to `schedule_state`, and sleeps for at most 30 seconds. Previously, at 02:01:30 it calculated the **same** tomorrow-02:00 instant and wrote the same row again. This repeated until the fire. The 30-second wakeup lets the scheduler notice wall-clock changes; the repeated database update was unnecessary. The loop now compares the result with its last successfully persisted state before writing ([`Scheduler.loop`](internal/scheduler/scheduler.go)).

`SetScheduleStateWithNext` executes `INSERT ... ON CONFLICT DO UPDATE` when called ([`store.go`](internal/store/store.go)). With 1,000 daily jobs, the old 30-second cadence could issue about 120,000 redundant updates per hour (1,000 × 120), plus real fire/reload work. This is a code-derived rate, not a measured throughput. The main SQLite pool allows one connection and uses WAL with `synchronous=FULL`, so those updates competed with run transitions and API reads and generated avoidable database/WAL work.

Every recalculation still calls `nextFireDistinct`. Previously this reparsed cron or `@every` text and reloaded the location on each call. The loop now compiles those inputs once. The DST check also jumps between time-zone transitions rather than walking in six-hour steps ([`scheduler.go`](internal/scheduler/scheduler.go)). The saving depends on job count, schedule frequency, timezone, and storage; the idle and next-fire benchmarks below measure representative cases.

### Implemented and possible follow-up work

1. **Implemented: suppress identical writes.** Each loop reads the persisted next fire on startup and tracks the last successfully persisted `last fire` and `next fire`. It writes after initialization, catch-up, and a fire, or when recomputation changes either value. The in-memory copy advances only after a successful database write. The 30-second clock check and the API's `next_fire_us` display remain in place ([`api.go`](internal/api/api.go), lines 431–450).
2. **Implemented: compile scheduling inputs once per loop.** The loop parses the cron expression or `@every` duration and resolves the timezone once, then reuses them for ordinary next-fire, DST gap/fold, and catch-up calculations. A reload creates fresh compiled inputs; the durable hash and watermark still reset the anchor after a schedule/timezone change.
3. **Implemented: retain unchanged loops on reload.** `Scheduler.Reload` compares complete definitions, keeps a live loop for each unchanged job, and joins changed or removed loops before starting replacements. Rapid reloads also treat canceled initialization as expected shutdown instead of logging an error for each job. In a 100-job benchmark, unchanged reloads took 93–94 µs and about 208 KB/op, while changing all definitions took 634–741 µs and about 530–535 KB/op. The old full-restart implementation measured about 509 µs and 335 KB/op under rapid reload, but its cancellation error logging contaminated that baseline, so it is not a clean speedup comparison.
4. **Implemented: jump to time-zone transitions.** `forwardTransition` uses `time.Time.ZoneBounds` rather than checking offsets every six hours. The gap check asks the cron parser for the first matching missing minute once, rather than testing every minute. `BenchmarkNextFireAnnual` improved from 13.09–13.14 µs to 1.22–1.27 µs for UTC, and from 24.50–24.79 µs to 3.05–3.15 µs for America/New_York. Tests compare next-fire results against the former search over several schedules, years, and time zones, including DST gaps and folds.
5. **Defer skipping next-fire recalculation between clock checks.** The loop could compare wall-clock elapsed time with monotonic elapsed time and recalculate only after a detected clock jump or a real fire. That requires handling small clock corrections and DST behavior without skipping a due occurrence. The measured full-daemon idle cost with 100 annual jobs is only 0.0739 CPU-ms/s in total, so the possible saving on this workload is smaller than that; retaining the existing 30-second recalculation is the safer tradeoff.

The implemented steps target redundant SQLite writes, parsing, and loop startup without changing when a job fires or when the UI sees its next fire. A 31-second idle sample spanning one clock check measured 0.0154 CPU-ms/s and 0.316 MiB Go heap with zero jobs, versus 0.0659 CPU-ms/s and 0.720 MiB with 100 annual UTC jobs. Both added 0 WAL bytes during the sample. These process measurements are small and host-specific; they exclude the HTTP server, executor, alert loop, and log archival. Wall-clock jumps and a reload near a fire still need targeted runtime measurement.

A separate 31-second full-daemon idle benchmark includes the Unix API listener, main and log stores, alert loop, and scheduler. With no jobs it measured 0.0154 CPU-ms/s, 0.536 MiB live Go heap, 37.33 MiB peak RSS, and 0 WAL-byte growth. With 100 annual UTC jobs it measured 0.0739 CPU-ms/s, 1.020 MiB live Go heap, 37.35 MiB peak RSS, and 0 WAL-byte growth. Each case ran in a fresh process and measured after startup and the initial maintenance sweep; peak RSS includes startup. These numbers are host-specific and do not represent a loaded daemon or a baseline before the changes.

## 2. Logs: bound work per frame and per reader

The live tail is capped at 5,000 frames/16 MiB per run and 64 MiB globally. It now uses a growing circular buffer and clears evicted payload references. The old front deletion shifted up to 4,999 frame headers per accepted frame. `Snapshot`, `Subscribe`, sequence order, and `discardHistoryThrough` retain their behavior.

Active writers now use one synchronous zstd encoder worker, a match window sized to the configured maximum line, and the library's lower-memory mode. Ordinary 1 MiB chunks use a 1 MiB window; a larger allowed line gets a larger power-of-two window, up to the previous 8 MiB default. This keeps the per-write `Flush` and file `Sync` durability boundary. In a 64-active-writer benchmark after one 1 KiB line per writer, live Go heap fell from 580 MiB to 95 MiB. With 1,000 repeated 1 KiB lines, `BenchmarkFrameEncoding` fell from 10.1–14.6 µs and about 9.8 KB allocated per frame to 2.4–3.1 µs and about 2.45 KB allocated per frame (three runs each). Compressed output was about 19.6 bytes per frame in both configurations. For 1,000 random 1 KiB lines, lower-memory mode allocated about 2.44 KB rather than 3.36 KB per frame; compressed output stayed at 1,051 bytes per frame and timings overlapped. These synthetic payloads cover compressible and incompressible cases, but not every log pattern.

A maximum-length 16 MiB random frame round-tripped through the file-backed writer and reader. Encoding and syncing it took 58 ms on `tmpfs` and 75 ms on ext4, allocated about 25 MB, and produced a 16,778,024-byte compressed chunk. This edge case uses the preserved 8 MiB encoder window; it does not have the ordinary small-line memory profile.

`Writer.Write` now encodes and syncs the caller's payload synchronously, then clones it only when the live tail or an SSE subscriber will retain it after the call returns. `Pipe` can still reuse its line buffer safely. When no live-tail quota was available and there were no subscribers, 1 KiB frame allocations fell from 2,318 to 1,294 bytes and from four to three allocations per write (three 1,000-write `tmpfs` runs). The ordinary retained-tail path still allocates about 2,450 bytes per frame. Tests mutate the caller's slice after a write and verify disk, subscriber, and tail contents remain unchanged; an oversized frame still evicts earlier tail entries as before.

The per-run lock now has allocation-free acquire/release calls, and each writer reuses its 24-byte frame-header buffer. On the same no-tail benchmark, three calibrated runs fell from 1,700–1,708 B/op and 3 allocs/op to 1,627–1,636 B/op and 1 alloc/op. Timing ranges overlapped at 2.97–3.13 µs/op, so this is an allocation improvement rather than a demonstrated throughput change.

The public `ReadContext` keeps its 16 MiB decoded response budget and its one-frame exception for an oversized valid frame. SSE backlog reads now use 1 MiB pages, while raw downloads use 4 MiB pages. Both reuse one zstd decoder across pages and close it when the backlog or download ends; a live SSE connection releases the decoder before waiting for new frames. An archive scan skips payload allocations for frames before the cursor and checks the page budget before allocating the next payload. Each page holds the run-tier lock so archival cannot move unseen frames past its cursor. Tests cover page boundaries, the maximum valid frame, and cursor continuity across archive, file, and live tiers.

For file-backed chunks, `ReadContext` now uses sealed-chunk `Last` metadata from the durable index to skip files wholly before `after`. It still scans file names and decodes unindexed chunks, so missing, corrupt, or incomplete indexes use the original recovery path. The archive database already skips chunks using `last_seq` ([`logdb.go`](internal/logdb/logdb.go)). This helps large worker logs, SSE reconnects, and raw downloads.

On this Linux/amd64 QEMU host, `BenchmarkLiveTailEviction` at a full 5,000-frame tail improved from 1,531–1,579 ns/op to 24.68–24.86 ns/op (five runs each), with 0 B/op and 0 allocs/op in both cases. `BenchmarkReadLateFileChunk`, which reads the last of 256 file chunks, improved from 5.68–5.84 ms/op and about 2.14 MB/op to 0.200–0.206 ms/op and about 104 KB/op (three runs each).

For a 20 MiB archive split into 20 chunks, a one-page backlog read improved from 15.6–16.3 ms and about 116.7 MB allocated to 6.8–7.2 ms and about 23.6 MB allocated by reusing the decoder across chunks. Reading the full backlog with 1 MiB pages improved from roughly 18–27 ms and 138.4 MB allocated to 10.8–11.5 ms and 27.8 MB allocated when one decoder was reused across pages. A raw download of an incompressible 20 MiB fixture took 18.8–19.7 ms and about 76.5 MB allocated with 4 MiB pages; 1 MiB pages took 25–27 ms and about 107.7 MB. In a 64-reader backlog benchmark, two zstd decoder workers per reader finished in 193 ms with about 514 MiB peak process RSS, versus 197 ms and about 569 MiB RSS using the library's default concurrency on this host. RSS includes the test harness and fixture. These are targeted benchmarks; they do not establish whole-daemon throughput or sustained RSS gains.

For 64 simultaneous HTTP SSE readers replaying a 4 MiB archived log, switching frame serialization from `json.Marshal` to `json.Encoder` preserved the exact SSE bytes while reducing burst allocations from about 860 MB to 456 MB. A fresh-process run's peak RSS fell from 339 MiB to 270 MiB; p95 completion changed from 129–143 ms to 114–130 ms across three runs per configuration. Later RSS numbers in each repeated run are process high-water marks, so they cannot be compared as independent per-run peaks. The streaming path releases its archive decoder before waiting for live frames.

A sustained worker-style benchmark wrote 2,000 1 KiB frames while the run stayed active and checkpointed to the archive three times. On ext4, a fresh-process run without SSE readers took 6.24 seconds (320 frames/s, 62.5 CPU-ms/s, 0.64 MiB live heap); with 16 concurrent live SSE readers it took 6.43 seconds (311 frames/s, 154 CPU-ms/s, 1.01 MiB live heap). Linux process writes were about 4,223 bytes per frame in both cases. The CPU counter includes the benchmark's HTTP clients. Every reader received all 2,000 frame IDs in order with no dropped event, and the finalized archive replayed the same sequence. This measures a paced 1 ms/frame source on one virtualized disk, not maximum ingest throughput.

Do **not** batch away `w.enc.Flush()` and `w.file.Sync()` per accepted frame ([`logstore.go`](internal/logstore/logstore.go), lines 395–402). The code explicitly treats `Write` as a durability boundary; reducing sync frequency would change crash behavior.

## 3. Metrics: reduce full-history scans without changing values

`RunMetrics` reads every run whose queue or end time intersects the requested window, plus active runs. The query is `queued_us>=? OR ended_us>=? OR status IN (...)`. Schema version 8 adds `idx_runs_end_time` on `ended_us`. With 30,000 old and 500 recent runs, `EXPLAIN QUERY PLAN` changed from `SCAN runs` to `MULTI-INDEX OR`, using the queue-time, end-time, and active-status indexes. `BenchmarkRunMetricsHistory` improved from 3.68–3.81 ms/op to 0.58–0.62 ms/op (three runs each). `BenchmarkRunTransitionIndexCost` measured creating and completing runs with and without the index; ranges overlapped at 68–85 µs/op across five runs on this host, so no write-cost conclusion is justified. Building the index during a 30,000-run migration took 7.0 ms on `tmpfs` and 13.5 ms on ext4, versus 0.46 ms and 7.2 ms for an empty database. SQLite used 487,424 additional nonfree page bytes for the 30,000-run index; a substantially larger installation still needs its own upgrade window.

The function now retains one compact duration sample per matching run and sorts it once. Global, per-job, and per-bucket exact p50/p95 values are selected as the sorted samples pass their ranks. The independent grouping test covers runs that contribute to just one scope. With 30,000 matching runs, `BenchmarkRunMetricsWindow` allocated 6.99 MB/op instead of 7.63 MB/op (about 8.5% less); time stayed around 32 ms/op. The frontend polls these metrics every 10–60 seconds on dashboard and metrics views ([`queries.ts`](web/src/queries.ts), lines 39–44; [`Dashboard.tsx`](web/src/pages/Dashboard.tsx), lines 24–37).

## 4. Alerts: wake only at the next deadline

The alert batcher now uses one resettable timer for the earliest pending `until` and disables it when the map is empty ([`alerts.go`](internal/alerts/alerts.go)). It recomputes the deadline after an item arrives, a batch flushes, or a channel reload splits a batch. Configured batch windows and immediate shutdown flush remain in place. The previous 100 ms ticker woke even with no pending batches. A 31-second isolated idle dispatcher sample measured 0.0138 CPU-ms/s and 0.412 MiB live Go heap on this host. There is no directly comparable pre-change dispatcher measurement, so the absolute saving is unproven.

## 5. Retention: process candidates in pages

The hourly sweep now selects eligible runs in pages of 128 and checks cancellation between pages and deletions ([`daemon.go`](internal/daemon/daemon.go); [`store.go`](internal/store/store.go)). The query uses a stable newest-first cursor, retains the newest terminal run even when it is older than `keep_for`, and skips runs protected by a live 24-hour idempotency key before deleting their logs. A new expression index supplies the retention order; a run/time index supports the idempotency check. The query plan uses both indexes. In a 1,000-run `tmpfs` transition benchmark, the retention index raised used SQLite pages by about 41 bytes per run and the timing ranges were 53–80 µs without it versus 74–92 µs with it. In a 200-run ext4 benchmark, timing ranges overlapped at 4.10–4.47 ms per create-and-finish transition; the index still added about 41 used page bytes per run. This cost is accepted in exchange for bounded retention selection and much lower sweep I/O.

After each page's logs are removed, the main store deletes eligible run rows in one guarded statement rather than committing a delete per run. Archive rows for the same page are now also removed in one transaction. The log store holds the relevant run locks, refuses to delete an active writer, and retries individual archive deletions if a batch fails; only IDs whose archive and file buffer were removed advance to main-store deletion. Tests inject failures into both database batches and verify that unaffected runs still progress.

The 2,000-run file-backed retention benchmark improved from 170–191 ms and about 1.73 MB allocated to 18–20 ms and about 1.15 MB allocated before archive batching (three `tmpfs` runs each). With archive batching it measured 19.0 ms and 1.37 MB; temporary lock bookkeeping adds some allocation. A direct 128-run main-store page benchmark improved from 7.60–8.31 ms/page to 0.74–0.82 ms/page, with WAL file growth falling from 30,512 to 872 bytes per removed run when automatic checkpointing was disabled. WAL growth is a database workload measure, not a physical device-write count.

For 2,000 retained runs with one tiny archived chunk each, the full sweep improved from 71.0 ms to 28.0 ms on `tmpfs`. On ext4, the same sweep improved from 8.03 seconds to 100–111 ms across three post-change runs. Linux process `write_bytes` during the measured sweep fell from about 39,919 to 1,770 bytes per deleted run; WAL file growth was uninformative because automatic checkpointing reused existing WAL space. The archive-only per-run baseline was 39.6–46.3 µs with 29,839 WAL bytes of growth per run when automatic checkpointing was disabled. An explicit transaction around each individual archive deletion was slower (45.8–58.7 µs) and barely changed WAL growth, so that version was discarded in favor of the page batch.

With 128 retained runs holding a synthetic 1 MiB archive blob each, deleting the eligible 127 in one page took 28 ms and about 2.5 KB of Linux process `write_bytes` per deleted run on ext4; archive finalization can wait behind that page's lock. Splitting archive pages into groups of 32 raised the small-blob ext4 sweep from about 100 to 192 ms and process writes from 1.77 to 3.04 KB per run; for large blobs it raised 28 to 42 ms and 2.5 to 3.9 KB per run. The 128-run page remains the chosen tradeoff for the hourly sweep.

## How to validate changes

The current benchmarks cover next-fire calculation, scheduler idle and reload, daemon idle and loaded HTTP operation, short and maximum-length frame ingestion, sustained active-worker output with concurrent live readers, live-tail eviction, archive and file-backed pagination, 64 concurrent HTTP SSE readers, raw download, `RunMetrics`, and retention with both tiny and large archived blobs. Use `TMPDIR` on a disk-backed filesystem when comparing sync cost or Linux process I/O; `tmpfs` is useful for isolating CPU and allocation changes. Compare CPU profiles, live heap/peak RSS, WAL growth, Linux process I/O, and API latency before and after each change.

Feature tests cover DST gap/fold schedules, catch-up and reload races, log crash recovery and stream cursor continuity, exact percentile values, and retention boundaries. Wall-clock jumps while the daemon is running remain a runtime measurement gap.
