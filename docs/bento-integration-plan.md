# Integration plan: keep minicrond standalone while Bento embeds per-app instances

Status: minicrond changes implemented for 0.2.0; Bento responsibilities remain external. Companion: `../../bento/specs/06-minicrond-migration-plan.md`. Bento is pre-production and is **not** migrating its legacy jobs. Minicrond must remain a good independent Linux tool: standalone CLI, UI, API, jobs, workers, and SQLite registry remain the normal user-facing authority. No Bento-owned namespaces, managed-definition API, registry ownership model, file-watch, or Bento-specific bootstrap import are requested.

Implementation decisions: kernel socket peers are the daemon UID or root; browser proxy access is supported only when TCP is disabled; and the general API offers `If-None-Match: *` to claim an unused definition name atomically. The proxy must still deny the token-rotation route and grant full operator access only to authorized app operators.

## Independent, generally useful improvements

### 1. Optional Unix-only daemon

Add an explicit `server.tcp_enabled = false` setting (default `true` to preserve standalone behavior). Require `server.unix_socket = true` in this mode and fail closed if there would be no listener. Skip TCP binding and initial TCP bearer-token creation in Unix-only mode; disable token rotation/exposure in its API and hide token controls in its UI, while retaining the mode-0600 Unix socket and Linux SO_PEERCRED same-UID check. Define how an existing token hash is retained safely if an operator later re-enables TCP. Ordinary standalone TCP + token + UI remains the default. A socket-only daemon still serves the full API, SPA/assets, and streams over the Unix socket: it is usable locally by its owner or through an **authenticated** external reverse proxy. Never make the socket world-readable or trust an arbitrary `X-Forwarded-User` header. Test multiple daemon instances on one host, port-free startup, socket/peer isolation, token behavior on mode changes, and shutdown cleanup. Document socket-only as a general service deployment option, not a Bento mode.

### 2. Numeric Linux identity without NSS

A daemon launched as an unprivileged numeric UID/GID in a minimal container may have no `/etc/passwd` entry. `internal/executor/executor.go` currently calls `user.Current()` even for jobs that do not request `run_as`. Fall back to actual process UID/GID **only when no `run_as` is set**, and use an explicitly configured `HOME`/working directory instead of silently using root's home. Set an appropriate `USER` only when known or supplied; never invent a host identity or allow an unprivileged daemon to switch users. Ensure the CLI can connect to `MINICRON_DATA/minicron.sock` under that UID and has a documented way to set `HOME`, `PATH` (including optional `/usr/local/bin`), and `TZ` for jobs. Test direct argv and shell jobs and workers as numeric UID, with and without passwd entries. Keep standalone defaults and `run_as` privilege checks intact.

### 3. UI when the transport already authenticates

The web SPA currently insists on a bearer token in `sessionStorage`, even when a reverse proxy has authenticated the viewer and forwards each request to the same-UID Unix socket. Add a **transport-aware login path** useful to any Unix-socket deployment: on load probe a normal protected API endpoint such as `/api/v1/daemon`; if it succeeds without a browser token, render the UI and make subsequent API/SSE/download calls without a token. If it returns 401, keep the existing standalone TCP token login; never infer privilege from a client-supplied header, a URL parameter, or a global daemon capability exposed to unauthenticated TCP users. Treat a later 401 as access revoked and clear sensitive cached UI state. Do not expose a token in the SPA, HTML, or API response for the proxy to pass to the browser; in Unix-only mode token settings and rotation must not be accessible through the proxied UI. Keep direct SPA framing default-denied (`X-Frame-Options: DENY`); an embedding proxy, after authenticating **every** request, is responsible for replacing that header with a narrowly scoped `frame-ancestors` policy. The UI must still work directly without Bento.

## Bento responsibilities, not minicrond features

- One app UID daemon per app owns **its own** registry, workers, runs, logs and private socket. Bento only supervises it, opens a correctly UID-scoped CLI context for app operators, and optionally installs its reserved _internal_ deploy drain / SQLite maintenance tasks. Root logrotate belongs to a separate root daemon. Ordinary app definitions live only in minicrond; Bento neither imports user definitions nor prunes them during apply.
- Bento must implement and test an authenticated per-app HTTP proxy and iframe. Its web server's optional Basic auth and unauthenticated loopback mode are not sufficient delegated authorization. The proxy, not minicrond, provides Bento user/session checks, CSRF/Origin enforcement, per-app routing, streaming, credential containment, framing policy and browser origin isolation. Because minicrond's UI uses root-relative SPA/API/asset routes, use a distinct origin per app with the UI at `/`, rather than a path prefix that would require changing minicrond's routing. A Bento-owned per-app UID-matched relay may be needed to reach the same-UID Unix socket; do **not** weaken Unix peer auth or add token-in-URL login to avoid that work. If per-app origins and transport isolation cannot be implemented safely, defer the iframe rather than expose a shared unauthenticated proxy.
- Avoid a new minicrond registry ownership protocol just to seed Bento's few internal jobs. Bento should use existing API/CLI validation, stable reserved names and idempotent updates, report drift/failure, and accept that an app user who controls that app's daemon can change that app's internal schedules. A generic atomic multi-definition operation is future work only if a concrete independent use case and failure tests justify it.

## Release and verification

- Update accepted ADR/acceptance docs, config JSON schema, API contract or generated UI types **only where behavior actually changes**, and document standalone defaults, Unix-only operation and security requirements for reverse proxying. Publish immutable checksum-verified linux/amd64 and linux/arm64 releases suitable for Bento's image build, but do not depend on Bento sources at build or runtime.
- Test default standalone UI login and CLI unchanged; Unix-only full API/UI with no TCP listener; same-UID and wrong-UID access; 401 fallback/revocation and live SSE without token; numeric-UID jobs/workers; framing remains denied when accessed directly. Run `go test ./...`, `go vet ./...`, `make check` and cross-architecture builds. Bento owns the end-to-end iframe/proxy and Docker isolation tests described in its companion plan.
