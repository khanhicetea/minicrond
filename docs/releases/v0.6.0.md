# minicrond 0.6.0

0.6.0 is the first stable release. Earlier tags were development builds.

## Compatibility

- **Fresh data directory required.** The metadata database (`minicron.db`) and
  the log archive (`minicron-logs.db`) now start at schema 1 and carry a SQLite
  `application_id`. Databases from pre-0.6 builds are refused at startup with
  `not created by minicrond 0.6 or later`; they are not upgraded. Stop the old
  daemon, move the data directory aside, start 0.6.0, and re-import your
  definitions (`minicrond export --format toml` on the old build first).
- From 0.6.0 on, schema changes ship with upgrade steps, and a binary refuses
  a newer schema than it knows.
- `[[alert_channel]]` is not accepted in bootstrap TOML. Channels live in the
  metadata database; create them in Settings → Alert channels or the API.

## What ships

- Cron jobs (5-field cron, descriptors, `@every`, per-job time zones,
  DST-safe) with catch-up, overlap, retries and a global concurrency gate.
- Supervised workers with restart policies, `max_restart_attempts` and
  `restart_backoff_max` (exponential backoff, never retired).
- **Execution first** ([ADR-16](../adr/0016-execution-first.md)): jobs and
  workers keep running when the metadata database or log storage fails (full,
  read-only, locked, stalled). History is written behind execution by a
  bounded background writer (1024 runs). Jobs can opt out per definition with
  `on_history_unavailable = "skip"` ([ADR-19](../adr/0019-history-unavailable-policy.md)).
- A bounded durable execution queue for triggers that find all slots busy
  ([ADR-9](../adr/0009-durable-execution-queue.md)).
- Two-tier logs: zstd chunk files written through on every frame with grouped
  fsync (`logs.durability = "batch"`, 2 s), archived into `minicron-logs.db`;
  chunks of 64 KiB or more are archived as files under `log-archive/`
  ([ADR-20](../adr/0020-log-archive-write-path.md)).
- A log disk budget whose free-space headroom is **on by default**
  (`logs.disk_min_free` = 512 MiB, clamped to a quarter of the filesystem):
  below it the oldest completed runs' logs are deleted early, ahead of
  retention age ([ADR-10](../adr/0010-log-disk-budget.md)). Set
  `logs.disk_min_free = 0` to turn it off, or `logs.disk_budget` to cap log
  disk use directly.
- Container support: built-in PID 1 init, `minicrond healthcheck`, embedded
  time zone data, `scheduler.shutdown_grace`, a `Dockerfile` and
  `examples/docker/`.
- REST + SSE API with an OpenAPI 3.1 contract, Unix socket and bearer-token
  TCP auth, optional Unix-only mode, and an embedded web UI with run metrics
  and a CPU/memory monitor.
- Database-backed Telegram alert channels with per-channel `notify_on`.

Default history limits: 10,000 runs and 7 days per definition
(`storage.keep_runs_default`, `storage.keep_for_default`); the log archive
keeps 30 days (`logs.db_keep_for`).

## Known limits

1. While storage fails, each run logs its log-open failure and each history
   retry (bounded by backoff, not rate limited). In read-only mode the history
   writer retries writes that cannot succeed until its 1024-run budget fills.
2. History written behind execution is lost on restart (ADR-16). After a crash
   during an outage, `catch_up = "latest"` may re-run an occurrence whose row
   was never stored.
3. The first writes of a locked-database episode each wait SQLite's 5 s busy
   handler before the circuit breaker opens.
4. Pending retries are kept in memory and lost on restart.
5. In `"batch"` durability an OS crash or power loss can lose about the last
   2 s of output, a finished run's included. A daemon crash loses nothing.
6. Process groups do not contain deliberately daemonized descendants;
   minicrond supervises trusted workloads and is not a sandbox.
7. Not yet measured: power-loss behavior of batched fsync, `EIO` during log
   archival, numerical log-volume targets.
